## medium: Hunyuan ZIP import extracts untrusted archives without traversal validation

id: fnd_sig-feat-library-25faef2bc4-3348_f17a5c87db
category: security
confidence: high
triage: confirmed-bug
status: open
feature: Python source root (feat_library_25faef2bc4)

evidence:
- blender_mcp_addon.py:2249-2255 (BlenderMCPServer.import_generated_asset_hunyuan_ai)
- blender_mcp_addon.py:2264-2273 (BlenderMCPServer.import_generated_asset_hunyuan_ai)
- blender_mcp_addon.py:1750-1777 (BlenderMCPServer.download_sketchfab_model)

The Hunyuan import path accepts an arbitrary HTTP(S) ZIP URL, downloads it, and calls extractall() directly. The same file contains explicit path-traversal checks in the Sketchfab ZIP path, showing the expected local pattern, but those checks are absent here. A malicious or compromised ZIP can attempt path traversal or unsafe archive entries during extraction before the OBJ import step.

recommendation:
Reuse the Sketchfab archive validation for Hunyuan before extraction: normalize each member, ensure the resolved target remains inside temp_dir using commonpath, reject absolute paths and traversal components, and only then extract. Prefer extracting members manually after validation.

test analysis:
No linked tests exercise Hunyuan ZIP import or malicious archive entries; the only discovered test-like files are unrelated terrain_data render scripts.

suggested regression test:
Add a unit test around the archive validation helper with traversal entries and assert import_generated_asset_hunyuan_ai rejects them before extraction.

minimum fix scope:
Hunyuan ZIP download/extraction path, ideally by factoring a shared safe ZIP extraction helper used by both Sketchfab and Hunyuan importers.

repro:
Enable Hunyuan3D and call import_generated_asset_hunyuan with zip_file_url pointing to a ZIP containing entries such as ../outside.txt or absolute-path-like names. The Hunyuan path extracts the archive without the validation used by the Sketchfab importer.

## high: MCP server accepts unauthenticated arbitrary Python execution

id: fnd_sig-feat-library-25faef2bc4-ab5b_6122055094
category: security
confidence: high
triage: confirmed-bug
status: open
feature: Python source root (feat_library_25faef2bc4)

evidence:
- blender_mcp_addon.py:58-59 (BlenderMCPServer.start)
- blender_mcp_addon.py:209-210 (BlenderMCPServer._execute_command_internal)
- blender_mcp_addon.py:421-431 (BlenderMCPServer.execute_code)

Starting the add-on opens a TCP listener and dispatches any JSON request with type execute_code to exec() with Python builtins still available. There is no authentication, shared secret, origin check, or user confirmation in the socket handler before executing code. Binding to localhost reduces remote exposure, but any local process can execute arbitrary Python inside the Blender process, including file and network operations available through builtins/imports.

recommendation:
Require an explicit per-session token or authenticated handshake before accepting commands, and gate execute_code behind a separate opt-in confirmation or remove it from the network API. At minimum, reject unauthenticated clients and log/deny execute_code unless the user has enabled a clear unsafe mode.

test analysis:
No tests are linked for this feature, and the repository test discovery only showed unrelated terrain_data render scripts rather than MCP protocol/security tests.

suggested regression test:
Add a socket-level test that sends execute_code without a valid token and asserts the server returns an authorization error and does not execute the payload.

minimum fix scope:
BlenderMCPServer connection protocol and execute_code registration/authorization path.

repro:
Start the BlenderMCP server, then connect to localhost:9876 and send a JSON object such as {"type":"execute_code","params":{"code":"open('/tmp/blender_mcp_pwned','w').write('x')"}}. The command is scheduled and executed without authentication.

## medium: Streaming downloads can hang indefinitely and leak response handles

id: fnd_sig-feat-library-25faef2bc4-e896_2eac758c0e
category: performance
confidence: high
triage: risk
status: open
feature: Python source root (feat_library_25faef2bc4)

evidence:
- fairfax_letter_finder.py:424-435 (ArchiveAPIClient.download_document_image)
- fairfax_letter_finder.py:199-205 (ArchiveAPIClient.search)
- fairfax_letter_finder.py:414-415 (ArchiveAPIClient.get_document)

The search and document metadata paths set a timeout and close responses in finally blocks, but download_document_image omits both. A slow or stalled image server can block the full search pipeline forever despite MAX_DOWNLOAD_RETRIES, because the first stream may never time out. Successful and failed streamed responses are also not explicitly closed, which can leave connections/file descriptors held in the session pool across many page downloads.

recommendation:
Pass timeout=self.timeout or a connect/read timeout tuple to the streaming GET and use a context manager, e.g. with self.session.get(..., stream=True, timeout=self.timeout) as response. Also clean up partial output files when a download fails mid-stream.

test analysis:
No linked tests cover archive image downloads, retry behavior, or stalled HTTP responses.

suggested regression test:
Add a test using a local fake server or mocked requests.Session.get that raises a read timeout during iter_content, then assert the method retries, closes the response, and returns False without leaving a partial file.

minimum fix scope:
ArchiveAPIClient.download_document_image download loop and failure cleanup.

repro:
Run the full search against an image URL served by a test HTTP server that accepts the connection and never sends the body. download_document_image blocks inside session.get/iter_content instead of timing out and retrying.

## low: Pytest test command is not reproducible from the only pip requirements file

id: fnd_sig-feat-library-d8e5ddfc31-61e5_2c2192ad9a
category: build-release
confidence: medium
triage: risk
status: open
feature: Python project Churchill (feat_library_d8e5ddfc31)

evidence:
- requirements.txt:1-9

The project metadata says the test command is pytest and pip/requirements.txt is the detected dependency source, but requirements.txt only installs runtime OCR/image/network/logging libraries. In a clean environment that follows the published pip metadata, pytest may be missing, so the configured test command can fail before any tests are collected.

recommendation:
Add a test/development dependency source that includes pytest, or add pytest to requirements.txt if this file is intended to provision both runtime and test environments. Update CI or clawpatch metadata to install that dependency set before running pytest.

test analysis:
No linked tests cover dependency metadata, and this failure occurs at environment setup time before application tests can run.

suggested regression test:
Add a CI smoke job that creates a fresh virtualenv, installs the declared pip dependency set, and runs python -m pytest or at least verifies import pytest succeeds before test execution.

minimum fix scope:
Introduce or reference a dev/test requirements file containing pytest, or include pytest in requirements.txt if that is the canonical install file.

repro:
Create a fresh virtualenv with only this file installed, then run: python -m pip install -r requirements.txt && pytest. If pytest is not already present globally, the test command is unavailable.
